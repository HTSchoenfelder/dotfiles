# macOS keyboard parity

## Goal

The macOS keyboard layer should preserve the physical shortcut habits used on
Linux and Hyprland. In GUI applications, `Ctrl` remains the user-facing action
modifier even when the native macOS command uses `Command` or `Option`.
Hammerspoon translates the intent; users should not have to remember a second
platform-specific shortcut.

Those physical habits originate in the fixed Advantage 360 Pro ZMK layout.
In particular, thumb-held Ctrl and the Space-held `mainMod` are intentional,
first-class shortcut inputs. The firmware boundary is documented in
[Keyboard input model](keyboard-input.md).

This is separate from window management. `mainMod` continues to own global
application and window navigation, while this layer owns shortcuts delivered to
the focused application and movement inside text.

## Ownership

| Component | Responsibility |
| --- | --- |
| Hammerspoon | Cross-application GUI editing, text navigation, VS Code native/webview text inputs and KeePassXC-specific translations |
| VS Code `keybindings.json` | Shared Linux/macOS workbench shortcuts, `Ctrl` actions outside editor text and terminal clipboard actions |
| Native terminal applications | Shell and TUI `Ctrl` sequences; Hammerspoon only translates explicit clipboard shortcuts |
| macOS applications | Receive native `Command` or `Option` events generated by Hammerspoon |

## Current implementation

`home/.hammerspoon/remapping.lua` is the lifecycle wrapper for the declarative
`modules/key_remapper.lua` key-down event tap. The module translates named keys,
keeps application boundaries explicit and accepts injected runtime dependencies
for behavioral tests. Kitty, Terminal and iTerm remain excluded from general GUI
translation. VS Code remains application-owned except for Accessibility-gated
editing and navigation in native and webview text inputs. There is no active
`DefaultKeyBinding.dict` or nix-darwin-owned native text remapping layer.

| Linux-shaped input | Current macOS delivery | Coverage |
| --- | --- | --- |
| `Ctrl+A/C/F/N/O/P/S/T/V/W/X/Z` | Matching `Command` shortcut | GUI applications and VS Code non-editor text inputs; not terminals; Chrome and KeePassXC app rules take precedence |
| `Ctrl+Shift+A/C/F/N/O/P/S/T/V/W/X/Z` | Matching `Command+Shift` shortcut | GUI applications and VS Code non-editor text inputs; not terminals; Chrome and KeePassXC app rules take precedence |
| `Ctrl+Shift+Z` and `Ctrl+Y` | `Command+Shift+Z` | GUI applications and VS Code non-editor text inputs; KeePassXC owns `Ctrl+Y` |
| `Ctrl+Left/Right` | Native word boundaries | GUI applications and VS Code non-editor text inputs; not terminals |
| `Ctrl+Shift+Left/Right` | Native word selection | GUI applications and VS Code non-editor text inputs; not terminals |
| `Ctrl+Backspace/Delete` | Native word deletion | GUI applications and VS Code non-editor text inputs; not terminals |
| `Home/End` and selection variants | Native line boundaries | GUI applications and VS Code non-editor text inputs; not terminals |
| `Ctrl+Home/End` and selection variants | Native document boundaries | GUI applications and VS Code non-editor text inputs; not terminals |
| `Ctrl+Shift+C/V` in native terminals | `Command+C/V` | Implemented |
| Other `Ctrl` keys in native terminals | Untranslated | Correctly preserved for shells and TUIs |

Zsh uses its standard Emacs navigation on NixOS/Hyprland and macOS: `Alt+B/F`
move backward/forward by one word; `Ctrl+A/E` move to the beginning/end of the
current line. There are no manual `Ctrl+Left/Right` or `Home/End` sequence
bindings. Hammerspoon leaves terminal navigation unchanged.
`setup/macos/setup-macos.sh` disables the native `Ctrl+Left/Right` Spaces
shortcuts so applications receive them; this does not add shell bindings.
fzf retains `Ctrl+R`, `Ctrl+T` and `Alt+C` for history, path and directory
selection. `Ctrl+X`, then `Ctrl+E`, edits the current input in Neovim and returns
it to the prompt before execution. See the
[shell editing reference](../readme.md#shell-editing).

Secure Input and applications that consume an event before Hammerspoon can
translate it remain platform limitations. These cases should be exceptions, not
the basis of the normal mapping.

## Chrome

Hyprland defines a custom browser navigation layer that deliberately overrides
some standard Chrome meanings:

| Input | Intended action | Hyprland | macOS today |
| --- | --- | --- | --- |
| `Ctrl+P` | Search tabs | `Ctrl+Shift+A` | Implemented as `Command+Shift+A` |
| `Ctrl+H` | Back | `Alt+Left` | Implemented as `Command+Left` |
| `Ctrl+J` | Previous tab | `Ctrl+Shift+Tab` | Implemented |
| `Ctrl+K` | Next tab | `Ctrl+Tab` | Implemented |
| `Ctrl+L` | Forward | `Alt+Right` | Implemented as `Command+Right` |

The macOS implementation targets native Chrome actions rather than copying the
Linux event literally. Back and Forward therefore use the native macOS Chrome
shortcuts `Command+Left/Right`; the visible action is the contract.

Common non-conflicting Linux Chrome shortcuts are covered for new and reopened
tabs, reload and hard reload, new and incognito windows, open file, bookmark and
bookmark-all, bookmark-bar visibility, clearing browsing data, numbered tab
selection and zoom. `Ctrl+W`, `Ctrl+F` and `Ctrl+S` use the general GUI map.
`Ctrl+Click` remains separate because the current event tap handles key-down
events, not mouse clicks. Native `Command` shortcuts remain available as an escape
hatch for actions intentionally displaced by the custom `P/H/J/K/L` layer:
`Command+Y` opens History, `Command+Shift+J` opens Downloads, `Command+L` focuses
the address bar and `Command+P` opens Print.

## VS Code

Hammerspoon normally returns VS Code key events unchanged. For editing and
text-navigation keys, it inspects the focused Accessibility element and translates
native text fields and webview text areas such as Codex Chat. Monaco editors are rejected
through their `AXCodeStyleGroup` ancestry, and the integrated terminal is rejected
through its terminal Accessibility identity. The shared
`home/.config/Code/User/keybindings.json` owns all remaining parity on Linux and
macOS; the file under `home/Library/Application Support/Code/User/` is a symlink
to it.

The current file deliberately keeps physical `Ctrl+P` and `Ctrl+Shift+P` for
Quick Open and the Command Palette, `Ctrl+,` and `Ctrl+Shift+,` for forward and
backward editor MRU selection, `Ctrl+E` for editor focus, `Ctrl+Shift+E/G/F` for
Explorer, Source Control and Find in Files, `Ctrl+Alt+S` for Save All, and
`Ctrl+Alt+I` for the Codex view. These keys also work in every VSCodeVim mode
and from terminal focus; `Ctrl+E` therefore replaces Vim's Normal-mode scrolling in
VS Code. `Ctrl+J` and `Ctrl+Shift+J` toggle and create an integrated terminal,
and `Ctrl+'` maximizes the panel. `Ctrl+J` also toggles from terminal
focus and creates a terminal if needed. `Ctrl+Shift+J` remains inactive in the
terminal. Both yield to VSCodeVim Insert mode, but VS Code owns them in Normal
mode; the equivalent Normal-mode downward motion remains available as `j`. An
explicit Insert-mode rule routes `Ctrl+J` back through VSCodeVim, where a
non-recursive mapping to `<Enter>` preserves the standard line break at the
modal cursor position. Space as leader and relative line numbers form the shared
presentation baseline. The complete target and current state are documented in
[VS Code Vim](vscode-vim.md).

Shared `!editorTextFocus && !terminalFocus` rules explicitly provide the same
standard `Ctrl` actions on Linux and macOS, including actions that match Linux
defaults. They apply in lists, Explorer, dialogs and other workbench surfaces:
selection, copy/cut/paste, undo/redo, find, save/save-as, close, new/open,
other sidebar and view commands, editor-group splitting and zoom. Native fields
and extension webview text inputs also receive the Accessibility-gated
Hammerspoon editing and text-navigation translation. All Monaco editor modes,
including Insert, remain outside that additional translation; the existing
explicit workbench exceptions listed above still apply.

`Ctrl+Shift+F` explicitly binds `workbench.action.findInFiles` in every focus
context, so Edit > Find in Files uses the Ctrl shortcut too.
The Search sidebar keeps its separate label binding to `workbench.view.search`
with VS Code's nonmatching `neverMatch =~ /doesNotMatch/` condition.

The Codex extension contributes two sidebar views depending on secondary-sidebar
support. `Ctrl+Alt+I` uses the generated focus command for the supported view;
whether the chat input gets the text cursor requires a live extension check.

The integrated terminal owns `Ctrl+C`, `Ctrl+A` and other shell/TUI inputs.
`Ctrl+E/P` run editor focus and Quick Open, while `Ctrl+Shift+P`, the view keys,
Save All and `Ctrl+J` also remain workbench-owned there. MRU selection,
new-terminal and panel-maximization controls still yield to terminal focus.
Enter still submits shell input. `Ctrl+Shift+C/V` invoke VS Code's terminal
copy/paste commands on both platforms, matching Kitty's physical keys.
Terminal-focused empty-command rules keep `Ctrl+A..Z` except `Ctrl+E/J/P` and the
other custom workbench keys from falling back to built-in or extension
shortcuts. This also lets `Ctrl+K` reach the shell without starting a VS Code
chord.

VS Code must remain application-owned for commands and editor behavior because
its `when` clauses can distinguish these contexts. Hammerspoon's narrow
Accessibility exception is limited to text input outside Monaco and the
terminal; enabling its generic translation for all of VS Code would break shell
and Vim behavior.

Known gaps and their follow-up tasks are tracked centrally in
[work.md](../work.md#macos-keyboard-parity).

## KeePassXC

Hammerspoon applies a KeePassXC-specific table before generic text/editing
translation. It preserves the default NixOS action keys while delivering the
macOS equivalent. In particular, `Ctrl+B/C/U/T/Y` copy username, password, URL,
TOTP, or password plus TOTP; `Ctrl+Shift+B/C/T` toggle username/password visibility
or show TOTP; `Ctrl+L` locks and `Ctrl+Shift+L` locks all databases.
`Ctrl+Shift+V` invokes entry Auto-Type. File, entry, settings, reports, search and
window actions use their normal Linux `Ctrl` shapes.

Database navigation preserves the actual Linux defaults: `Ctrl+Tab` and
`Ctrl+Shift+Tab` deliver `Option+Tab` and `Option+Shift+Tab`; `Ctrl+PageUp/PageDown`
and their shifted group-navigation variants deliver `Command` instead of `Ctrl`.
`Alt+1..9` selects database tabs through `Command+1..9`. `Ctrl+F4` closes the
database through `Command+W`. Group sorting uses `Ctrl+Up/Down` through
`Command+Up/Down`. KeePassXC already keeps physical `Ctrl+H/Shift+H` for SSH-agent
actions on macOS, so these pass through. Plain keys, Alt-based entry movement and
global Auto-Type combinations are not translated.

Native `Command` shortcuts remain available. KeePassXC 2.8 supports internal
shortcut customization, but the dotfiles deliberately keep macOS translation in
Hammerspoon rather than synchronizing the whole writable `keepassxc.ini`, which
also contains local application and security preferences. The application owns
its configuration, database and global Auto-Type settings. Clipboard history
continues to exclude KeePassXC.

## Target text contract

| Physical input | Native macOS action outside terminals |
| --- | --- |
| `Ctrl+Left/Right` | `Option+Left/Right` |
| `Ctrl+Shift+Left/Right` | `Option+Shift+Left/Right` |
| `Ctrl+Backspace/Delete` | `Option+Backspace/Delete` |
| `Home/End` | `Command+Left/Right` |
| `Shift+Home/End` | `Command+Shift+Left/Right` |
| `Ctrl+Home/End` | `Command+Up/Down` |
| `Ctrl+Shift+Home/End` | `Command+Shift+Up/Down` |

The contract describes outcomes, not a promise that every application uses the
same underlying native event. Application-specific handling is acceptable when it
preserves the physical keys and visible result.
