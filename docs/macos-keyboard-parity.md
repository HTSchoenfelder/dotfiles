# macOS keyboard parity

## Goal

The macOS keyboard layer should preserve the physical shortcut habits used on
Linux and Hyprland. In GUI applications, `Ctrl` remains the user-facing action
modifier even when the native macOS command uses `Command` or `Option`.
Hammerspoon translates the intent; users should not have to remember a second
platform-specific shortcut.

This is separate from window management. `mainMod` continues to own global
application and window navigation, while this layer owns shortcuts delivered to
the focused application and movement inside text.

## Ownership

| Component | Responsibility |
| --- | --- |
| Hammerspoon | Cross-application GUI editing, text navigation and small application-specific translations |
| VS Code `keybindings.json` | Context-aware editor, list, explorer, Vim and integrated-terminal behavior |
| Native terminal applications | Shell and TUI `Ctrl` sequences; Hammerspoon only translates explicit clipboard shortcuts |
| macOS applications | Receive native `Command` or `Option` events generated by Hammerspoon |
| Karabiner-Elements | No active responsibility |

`home/.config/karabiner/karabiner.json` is currently legacy configuration.
Karabiner-Elements is neither installed nor running. The file contains both a
global `Ctrl`/`Command` swap and per-device swaps, so it must not silently become
part of the active design. Either it should be removed or a future physical-key
layer must be designed explicitly without duplicating Hammerspoon.

## Current implementation

`home/.hammerspoon/remapping.lua` is the lifecycle wrapper for the declarative
`modules/key_remapper.lua` key-down event tap. The module translates named keys,
keeps application boundaries explicit and accepts injected runtime dependencies
for behavioral tests. Kitty, Terminal and iTerm remain excluded from general GUI
translation, and VS Code remains application-owned. There is no active
`DefaultKeyBinding.dict` or nix-darwin-owned native text remapping layer.

| Linux-shaped input | Current macOS delivery | Coverage |
| --- | --- | --- |
| `Ctrl+A/C/V/X/F/S/W/Z` | Matching `Command` shortcut | GUI applications outside VS Code and terminals |
| `Ctrl+Shift+A/C/V/X/F/S/W/Z` | Matching `Command+Shift` shortcut | GUI applications outside VS Code and terminals |
| `Ctrl+Shift+Z` and `Ctrl+Y` | `Command+Shift+Z` | GUI applications outside VS Code and terminals |
| `Ctrl+Left/Right` | `Option+Left/Right` | Implemented outside VS Code and terminals |
| `Ctrl+Shift+Left/Right` | `Option+Shift+Left/Right` | Implemented outside VS Code and terminals |
| `Ctrl+Backspace/Delete` | `Option+Backspace/Delete` | Implemented outside VS Code and terminals |
| `Home/End` and selection variants | Native line boundaries | Implemented outside VS Code and terminals |
| `Ctrl+Home/End` and selection variants | Native document boundaries | Implemented outside VS Code and terminals |
| `Ctrl+Shift+C/V` in native terminals | `Command+C/V` | Implemented |
| Other `Ctrl` keys in native terminals | Untranslated | Correctly preserved for shells and TUIs |

The Zsh configuration explicitly binds the terminal sequences for
`Ctrl+Left/Right` to `backward-word` and `forward-word`. Terminal word navigation
is therefore shell-owned rather than translated to a macOS GUI shortcut.

Secure Input and applications that consume an event before Hammerspoon can
translate it remain platform limitations. These cases should be exceptions, not
the basis of the normal mapping.

## Chrome

Hyprland defines a custom browser navigation layer that deliberately overrides
some standard Chrome meanings:

| Input | Intended action | Hyprland | macOS today |
| --- | --- | --- | --- |
| `Ctrl+P` | Search tabs | `Ctrl+Shift+A` | Implemented as `Command+Shift+A` |
| `Ctrl+H` | Back | `Alt+Left` | Implemented as `Command+Left` |
| `Ctrl+J` | Previous tab | `Ctrl+Shift+Tab` | Implemented |
| `Ctrl+K` | Next tab | `Ctrl+Tab` | Implemented |
| `Ctrl+L` | Forward | `Alt+Right` | Implemented as `Command+Right` |

The macOS implementation targets native Chrome actions rather than copying the
Linux event literally. Back and Forward therefore use the native macOS Chrome
shortcuts `Command+Left/Right`; the visible action is the contract.

Common non-conflicting Linux Chrome shortcuts are covered for new and reopened
tabs, reload and hard reload, new and incognito windows, open file, bookmark and
bookmark-all, bookmark-bar visibility, clearing browsing data, numbered tab
selection and zoom. `Ctrl+W`, `Ctrl+F` and `Ctrl+S` use the general GUI map.
`Ctrl+Click` remains separate because the current event tap handles key-down
events, not mouse clicks. Native `Command` shortcuts remain available as an escape
hatch for actions intentionally displaced by the custom `P/H/J/K/L` layer:
`Command+Y` opens History, `Command+Shift+J` opens Downloads, `Command+L` focuses
the address bar and `Command+P` opens Print.

## VS Code

Hammerspoon returns every VS Code key event unchanged. The shared
`home/.config/Code/User/keybindings.json` therefore owns all parity on Linux and
macOS; the file under `home/Library/Application Support/Code/User/` is a symlink
to it.

The current file covers Quick Open, the Command Palette, save, find, undo/redo,
cut, select all, search, explorer focus, terminal creation/toggling and several
view-specific copy actions. General `Ctrl+C/V` now pair the native menu aliases
with VS Code's effective editor clipboard actions while `!terminalFocus`; the
integrated terminal retains its native `Ctrl+C/V`. VSCodeVim separately owns
`Ctrl+H/L` in Normal mode for previous and next buffers.

The remaining gaps are material:

- Word, line and document navigation and their selection variants are missing.
- `Ctrl+H/L` only work in VSCodeVim Normal mode, not consistently in editor input,
  lists, dialogs or other workbench surfaces.
- Several copied rules are duplicated and some have overly broad or absent `when`
  clauses.
- The integrated terminal maps `Ctrl+A` to Select All and `Ctrl+F` to terminal
  Find, overriding normal shell beginning-of-line and forward-character behavior.
- Editor, Vim modes, lists, Quick Pick, webviews and the integrated terminal do
  not yet have an explicit conflict matrix.

VS Code must remain application-owned because its `when` clauses can distinguish
these contexts. Re-enabling the generic Hammerspoon translation for VS Code would
lose that information and would break terminal and Vim behavior.

## Remaining work

The generic GUI text contract, Chrome parity and the testable Hammerspoon module
are implemented. The remaining work is deliberately narrower:

1. Audit VS Code's editor, Vim, list, Quick Pick, webview and integrated-terminal
   contexts. Reduce the current keybindings to intentional rules with precise
   `when` clauses, then add text navigation without stealing shell or modal keys.
2. Decide separately whether Chrome `Ctrl+Click` belongs in Hammerspoon or an
   explicitly activated physical-input layer.
3. Remove the inactive Karabiner configuration, or document and install a narrowly
   scoped device layer. It must never overlap transformations owned by
   Hammerspoon.
4. Add a manual verification matrix for native Cocoa inputs, Chrome page and
   address fields, VS Code editor/Vim/list/terminal contexts, Kitty and secure
   inputs. Automated event tests cannot prove every application boundary.

## Target text contract

| Physical input | Native macOS action outside terminals |
| --- | --- |
| `Ctrl+Left/Right` | `Option+Left/Right` |
| `Ctrl+Shift+Left/Right` | `Option+Shift+Left/Right` |
| `Ctrl+Backspace/Delete` | `Option+Backspace/Delete` |
| `Home/End` | `Command+Left/Right` |
| `Shift+Home/End` | `Command+Shift+Left/Right` |
| `Ctrl+Home/End` | `Command+Up/Down` |
| `Ctrl+Shift+Home/End` | `Command+Shift+Up/Down` |

The contract describes outcomes, not a promise that every application uses the
same underlying native event. Application-specific handling is acceptable when it
preserves the physical keys and visible result.
